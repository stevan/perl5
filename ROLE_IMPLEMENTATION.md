# Proto-Role Implementation Notes

This document sketches out how the proto-role algebra described in
ROLE_ALGEBRA.md could be implemented in Perl core. It is a
conversation starter, not a formal spec.

---

## 1. Data Structures

### 1.1 Method Slot

A method slot is the atomic unit of the algebra. It carries its
own name (following the SLOTS.md lineage and the Perl sketch in
role-algebra-sketch.pl) rather than being keyed in a map.

```c
typedef struct method_slot {
    SV           *name;       /* the method name (shared HEK-backed SV) */
    origin_set_t  origins;    /* bitset encoding (see §1.3) */
    CV           *cv;         /* the method CV; NULL for Required */
    /* provenance — used for construction-time checks and diagnostics */
    PADNAME      *from_field; /* non-NULL if generated by :reader/:writer */
} method_slot_t;
```

**Why name-in-the-slot?** The alternative is a name-indexed map
(HV or sorted array of key-value pairs) where the name lives in
the map structure. Embedding the name in the slot is preferable
for several reasons:

- **Self-describing.** A slot is a complete unit of information.
  You can pass it around, store it in an array, or log it without
  needing to carry its key separately. This matters during the
  composition fold: when merging two sorted arrays, you compare
  by `slot->name` directly — the slot IS the entry.

- **Matches existing core patterns.** PADNAME carries its own name
  and metadata. PADNAMELIST is a flat array of PADNAMEs. A proto-
  role's slot array is structurally identical: a flat array of
  self-describing entries. This is the idiom the codebase already
  uses for the closely related concept of field declarations.

- **No map overhead for small collections.** Most roles define
  5–15 methods. A sorted array of method_slot_t is compact,
  cache-friendly, and avoids the per-bucket overhead of an HV.
  Binary search for lookup is O(log n) on small n — negligible.

The slot's `tag` is implicit in the `origins` bitset (see §1.3),
so no explicit enum is needed.

### 1.2 Field Slot

```c
typedef struct field_slot {
    PADNAME      *padname;    /* the PADNAME (carries name, sigil, fieldinfo) */
    origin_set_t  origins;    /* bitset encoding */
} field_slot_t;
```

Field slots reuse the existing PADNAME infrastructure. The
PADNAME already carries the field's name, sigil, default
expression, `:param` info, and fieldstash. We add the origin
bitset for composition tracking.

There is no Required variant for fields — fields are always
concrete declarations, so `origins` is always non-zero.

### 1.3 Origin Set (Bitset)

```c
typedef uint32_t origin_set_t;
```

At the start of a composition pipeline, each participating proto-
role is assigned a small integer ID (0, 1, 2, ...). An origin set
is a bitset over these IDs.

```c
/* Required:   origins == 0   (no origin — pure obligation) */
/* Defined:    popcount == 1  (exactly one origin) */
/* Conflicted: popcount >  1  (multiple origins) */

/* compose two method slots (same name): */
static inline origin_set_t
compose_origins(origin_set_t a, origin_set_t b) {
    return a | b;
}
```

**Why a bitset?** The entire method algebra reduces to bitwise OR.
Required (0) is the identity for OR. Same-origin Defined slots OR
to themselves (idempotent). Different-origin Defined slots OR to
a multi-bit value (Conflicted). Conflicted absorbs via union = OR.
The tag is the popcount. No branches, no heap allocation.

32 bits supports up to 32 roles in a single composition, which is
far more than any real program needs. If someone hits the limit, a
fallback to a dynamic bitset (an array of uint32_t) is possible
but likely never needed.

Each proto-role also keeps a mapping from bit position back to the
actual stash pointer, for error messages and `->DOES` checks:

```c
typedef struct {
    HV    *stashes[32];   /* bit position → stash pointer */
    U8     next_id;       /* next available bit position */
} origin_map_t;
```

### 1.4 Proto-Role

```c
typedef struct proto_role {
    HV              *stash;          /* the class/role stash (origin) */
    U8               origin_id;     /* this proto-role's bit in origin_set_t */

    method_slot_t   *method_slots;   /* sorted by name */
    UV               method_count;

    field_slot_t    *field_slots;    /* sorted by name */
    UV               field_count;

    AV              *adjust_blocks;  /* ADJUST CVs (not part of the algebra) */
} proto_role_t;
```

**Why sorted arrays?** The core composition operation is pointwise
merge of two proto-roles' slot arrays. With sorted arrays, this is
a merge-join: walk both arrays in parallel, compare names, apply
`compose_origins` when names match, pass through when a name
appears in only one. This is O(n+m), cache-friendly, and produces
a sorted result ready for the next fold step. No hashing needed
in the hot path.

The proto-role struct is allocated at parse time and populated
incrementally as fields and methods are parsed. At seal time it
enters the composition pipeline. It does not replace `xpvhv_aux` —
it is a companion structure referenced from it.

### 1.5 Relationship to Existing Structures

The proto-role does not replace the stash or the `xpvhv_aux`
class metadata. It lives alongside them:

```
xpvhv_aux (existing)
├── xhv_class_superclass    (unchanged)
├── xhv_class_fields        (PADNAMELIST — still needed for initfields)
├── xhv_class_adjust_blocks (unchanged)
├── xhv_class_param_map     (unchanged)
├── xhv_class_pending_roles (replaced by proto_role references)
├── xhv_class_roles         (unchanged — for ->does())
└── xhv_class_proto_role    (NEW — pointer to proto_role_t)
```

The proto-role is the staging area. The stash is the final
destination. At seal time, the composed and resolved proto-role's
contents are installed into the stash (method CVs) and the
PADNAMELIST (field indices). After sealing, the proto-role MAY
be retained for introspection and `->DOES` checks, or freed if
memory is a concern.

## 2. Lifecycle (High Level)

This section describes what happens at each stage, without
specifying how. The goal is an end-to-end understanding of the
pipeline.

### 2.1 Parse Time — Proto-Role Construction

When the parser enters a `class` or `role` block, a proto-role
is allocated and attached to the stash's `xpvhv_aux`.

As the parser encounters declarations in the body:

- **`field $x`** — A field slot is added to the proto-role's
  field array. The PADNAME and fieldinfo are created as they are
  today.

- **`field $x :reader`** — A field slot is added as above. In
  addition, the accessor CV is compiled (as today), but instead
  of being installed into the stash immediately via `newATTRSUB`,
  it is recorded in the proto-role's method array as a method slot
  with provenance pointing back to the field. The CV is held by
  the proto-role.

- **`method foo { ... }`** — The method CV is compiled as today.
  A method slot is added to the proto-role's method array with
  explicit provenance (not generated from a field).

- **`method foo;`** — A Required method slot is added (origins = 0,
  cv = NULL).

- **`:does(RoleName)`** — The role stash is recorded as a pending
  role (as today). The actual composition is deferred to seal time.

**Construction-time collision detection:** As method slots are
added, the proto-role checks for same-name collisions between
generated accessors (§3.2 of ROLE_ALGEBRA.md). This is a simple
check during insertion — "does a method with this name already
exist in my array, and is it also generated?" If so, the collision
is recorded. If an explicit method later resolves it, the collision
is cleared (with a redefine warning).

At the end of parsing, the proto-role's slot arrays are sorted by
name (or maintained in sorted order during insertion). The proto-
role is ready for composition.

### 2.2 Seal Time — Composition

When `class_seal_stash` is called, the composition pipeline runs.

**Step 1: Gather proto-roles.** The consumer's proto-role and the
sealed proto-roles of all `:does` roles are collected. Each is
assigned a bit position in the origin bitset.

**Step 2: Compose.** All proto-roles are folded together using
pairwise sorted merge. For each pair of method slots with the
same name, `compose_origins` (bitwise OR) produces the composed
origin set. For field slots, the same operation. The result is a
single composed proto-role.

**Step 3: ADJUST blocks.** ADJUST blocks are collected from all
composed roles with diamond deduplication (by CV identity).

The composed proto-role now holds the complete picture: every
method and field from all sources, with their origin bitsets
reflecting where they came from.

### 2.3 Seal Time — Resolution

The composed proto-role is checked against the consumer's explicit
methods:

**For each method slot in the composed result:**

- If `popcount(origins) == 0` (Required): check if the consumer
  provides an explicit method with this name (or, for classes, if
  one is inherited). If not, record an error.

- If `popcount(origins) > 1` (Conflicted): check if the consumer
  provides an explicit method with this name. If yes, the conflict
  is resolved. If not, record an error.

- If `popcount(origins) == 1` (Defined): no action needed — this
  method will be installed.

**For each field slot in the composed result:**

- If `popcount(origins) > 1` (Conflicted): always an error.

All errors are collected and reported together in a single
diagnostic.

### 2.4 Seal Time — Installation

After resolution succeeds (no errors), the composed proto-role's
contents are installed:

- **Methods:** Each Defined method's CV is installed into the
  stash. For role methods that reference fields, the CV is cloned
  with the field index offset (as today).

- **Fields:** Field indices are resolved from relative to absolute
  (as today). The PADNAMELIST is populated.

- **ADJUST blocks:** Collected and attached to the class's
  adjust_blocks AV (as today), with field offset cloning.

- **Accessors:** Generated accessor CVs from the proto-role's
  method slots (those with `from_field != NULL`) are installed
  into the stash at this point — not during parsing.

The stash is marked as sealed.

### 2.5 Summary

```
Parse time:
  class Foo :does(R1) :does(R2) {
      field $x :reader;        →  proto-role gets field slot + method slot (generated)
      field $y :param;         →  proto-role gets field slot
      method bar { ... }       →  proto-role gets method slot (explicit)
      method baz;              →  proto-role gets Required slot
  }                            →  proto-role is complete, arrays sorted

Seal time:
  1. Gather:    [FooPR, R1PR, R2PR]
  2. Compose:   sorted-merge fold → composed proto-role
  3. Resolve:   check Conflicted/Required vs Foo's explicit methods → errors or OK
  4. Install:   methods → stash, fields → PADNAMELIST, ADJUST → AV
  5. Seal:      mark stash as sealed
```

## 3. Technical Details

### 3.1 Where the Proto-Role Struct Lives

A new `proto_role_t` pointer is added to `struct xpvhv_aux`:

```c
/* in hv.h, within struct xpvhv_aux: */
proto_role_t *xhv_class_proto_role;  /* NEW */
```

Allocated in `Perl_class_setup_stash` (class.c:433), freed (or
retained) during sealing. The existing `xhv_class_pending_roles`
AV is kept for now (it holds stash pointers collected during
parsing) but could eventually be folded into the proto-role
lifecycle.

### 3.2 Accessor CV Generation — Deferred Installation

Currently, `apply_field_attribute_reader` (class.c:2096) compiles
the accessor CV and calls `newATTRSUB`, which installs it directly
into the stash. This is the root cause of silent overwrites.

The change: after compiling the CV, instead of `newATTRSUB`
installing it into the stash, we hold the CV in the proto-role's
method slot array. The CV is still compiled at parse time (it
needs the pad and field import), but installation is deferred.

This requires a way to compile a method CV without installing it.
Options:

- **Use `newATTRSUB` but intercept the installation.** The current
  `newATTRSUB` path goes through `Perl_newATTRSUB_x` which calls
  `hv_store` on the stash. We could add a flag or use a different
  entry point that returns the CV without storing it.

- **Compile the CV manually.** The reader/writer generation code
  already builds the optree by hand. Instead of calling
  `newATTRSUB(floor_ix, nameop, ...)`, we could call a lower-level
  function that produces the CV without the stash side-effect. The
  existing `cv_clone` / pad machinery would still work.

The first option is less invasive. A possible approach: introduce
a `newMETHOD_CV` helper that mirrors `newATTRSUB` but returns the
CV without installing it into the stash. This would be useful
beyond just accessors — any method that should be held in the
proto-role rather than immediately installed.

### 3.3 The Composition Fold

The current `S_class_compose_roles` (class.c:1011) is a ~300-line
function that iterates roles, walks stash entries for methods,
walks PADNAMELIST for fields, uses temporary HVs for conflict
tracking, and croaks on first error. It interleaves composition,
installation, and error reporting in a single pass.

The new approach separates these concerns:

```c
/* Phase 1: Assign origin IDs and gather proto-roles */
static void
S_proto_role_assign_ids(pTHX_ proto_role_t *consumer,
                        AV *role_stashes, origin_map_t *map);

/* Phase 2: Pairwise sorted merge of two proto-roles */
static proto_role_t *
S_proto_role_compose(pTHX_ proto_role_t *left, proto_role_t *right);

/* Phase 3: Fold N proto-roles via repeated pairwise merge */
static proto_role_t *
S_proto_role_compose_all(pTHX_ proto_role_t **roles, UV count);

/* Phase 4: Resolution — check composed result, collect errors */
static AV *
S_proto_role_resolve(pTHX_ proto_role_t *composed,
                     proto_role_t *consumer, HV *stash);

/* Phase 5: Installation — install resolved result into stash */
static void
S_proto_role_install(pTHX_ proto_role_t *resolved,
                     HV *stash, origin_map_t *map);
```

The core of the merge is tight:

```c
/* Merge two sorted method-slot arrays. */
static method_slot_t *
S_merge_method_slots(pTHX_ method_slot_t *a, UV a_count,
                           method_slot_t *b, UV b_count,
                           UV *out_count)
{
    UV max = a_count + b_count;
    method_slot_t *out = Newx(out, max, method_slot_t);
    UV ai = 0, bi = 0, oi = 0;

    while (ai < a_count && bi < b_count) {
        int cmp = sv_cmp(a[ai].name, b[bi].name);
        if (cmp < 0)
            out[oi++] = a[ai++];
        else if (cmp > 0)
            out[oi++] = b[bi++];
        else {
            /* same name — compose */
            out[oi] = a[ai];  /* inherit name, cv from left */
            out[oi].origins = a[ai].origins | b[bi].origins;

            /* If origins differ, this is a conflict. The CV from
             * left is kept as representative, but it won't be
             * installed — resolution will either replace it with
             * an explicit consumer method or report an error. */
            if (a[ai].origins != b[bi].origins &&
                popcount(out[oi].origins) > 1) {
                /* Conflicted — CV choice is arbitrary since it
                 * won't be used unless resolved. Keep left's. */
            }
            oi++; ai++; bi++;
        }
    }

    /* copy remaining */
    while (ai < a_count) out[oi++] = a[ai++];
    while (bi < b_count) out[oi++] = b[bi++];

    *out_count = oi;
    return out;
}
```

This replaces the temporary `composed_fields` HV and the inline
stash-walking method conflict detection in the current code.

### 3.4 Resolution and Error Collection

Currently, conflicts produce an immediate `croak`. The new
approach collects errors into an AV:

```c
static AV *
S_proto_role_resolve(pTHX_ proto_role_t *composed,
                     proto_role_t *consumer, HV *stash)
{
    AV *errors = NULL;  /* lazily allocated */

    for (UV i = 0; i < composed->method_count; i++) {
        method_slot_t *slot = &composed->method_slots[i];
        int pc = popcount(slot->origins);

        if (pc == 0) {
            /* Required — check consumer explicit methods and inheritance */
            if (!consumer_has_explicit(consumer, slot->name) &&
                !class_inherits_method(stash, slot->name)) {
                if (!errors) errors = newAV();
                av_push(errors, new_error_required(slot));
            }
        }
        else if (pc > 1) {
            /* Conflicted — only consumer explicit method resolves */
            if (!consumer_has_explicit(consumer, slot->name)) {
                if (!errors) errors = newAV();
                av_push(errors, new_error_conflict(slot));
            }
        }
    }

    /* Field conflicts are always errors */
    for (UV i = 0; i < composed->field_count; i++) {
        field_slot_t *slot = &composed->field_slots[i];
        if (popcount(slot->origins) > 1) {
            if (!errors) errors = newAV();
            av_push(errors, new_error_field_conflict(slot));
        }
    }

    return errors; /* NULL = no errors */
}
```

The `consumer_has_explicit` check is a binary search on the
consumer's sorted method slot array, filtered by provenance
(only explicit methods, not generated accessors).

If errors are found, they are formatted into a single diagnostic
showing all problems at once, then `croak`ed.

### 3.5 Field Index Assignment

Field index resolution happens after composition, as today. The
key change: diamond-composed fields (same origin, same name) must
be deduplicated before indices are assigned.

Currently, `S_class_compose_roles` advances `next_fieldix` per
role without checking for diamonds, which can allocate duplicate
slots. With the proto-role approach, diamond fields are already
deduplicated by the composition algebra (same origin → idempotent
merge). The composed field array contains each field exactly once,
and indices are assigned by walking this array sequentially.

The field offset mechanism for role methods (cloning CVs with
adjusted field indices) remains unchanged — it is applied during
installation (§2.4) based on the resolved field indices.

### 3.6 Changes to `class_seal_stash`

The current `Perl_class_seal_stash` (class.c:1321) would be
restructured roughly as:

```
Perl_class_seal_stash(stash):
    1. Seal superclass if needed (unchanged)
    2. Initialize field offset from superclass (unchanged)
    3. NEW: Finalize proto-role construction
       - Sort slot arrays if not already sorted
       - Check for unresolved construction-time conflicts
    4. NEW: Run composition pipeline
       - Assign origin IDs to all participating proto-roles
       - Fold via pairwise sorted merge
       - Resolve against consumer's explicit methods
       - Report all errors or proceed
    5. NEW: Install composed result
       - Install method CVs into stash (with field offset cloning)
       - Collect ADJUST blocks (with dedup and offset cloning)
    6. Resolve field indices (largely unchanged)
    7. Build initfields CV (largely unchanged)
    8. Seal method field-maps (unchanged)
    9. Mark stash as sealed
```

Steps 3–5 replace the current `S_class_compose_roles` call and
the ad-hoc stash walking for accessor installation.

### 3.7 Files Affected

**class.c** — The bulk of the changes. `S_class_compose_roles` is
replaced by the composition pipeline functions. Accessor generation
(`apply_field_attribute_reader`, `apply_field_attribute_writer`) is
modified to hold CVs in the proto-role instead of installing them
via `newATTRSUB`. `Perl_class_seal_stash` is restructured.

**class.h** (or new header) — The proto-role struct definitions,
method/field slot types, origin_set_t, and the composition API.
These could live in a new `proto_role.h` or be added to the
existing class-related section of `hv.h`.

**hv.h** — Addition of `xhv_class_proto_role` pointer to
`struct xpvhv_aux`.

**pad.h** — Possibly minor changes to `padname_fieldinfo` if we
want to store origin_id or back-references to the proto-role.
Likely minimal.

**op.c / pp_hot.c** — No changes expected. The OP_METHSTART
field offset mechanism is unchanged. The runtime cost of method
dispatch is unchanged. All proto-role work is compile-time.

### 3.8 What Doesn't Change

- **Runtime method dispatch.** No changes to how methods are called
  at runtime. The stash is still the dispatch table.
- **Object layout.** ObjectFIELDS array, field access via
  OP_METHSTART — all unchanged.
- **OP_INITFIELD / initfields CV.** The field initialization
  pipeline is unchanged, just fed from the composed proto-role
  instead of ad-hoc role walking.
- **`:isa` inheritance.** Superclass handling is orthogonal to
  role composition and stays as-is.
- **`->does` runtime check.** Still walks `xhv_class_roles` AV.

### 3.9 Open Questions

**Proto-role retention.** Should the proto-role be freed after
sealing or retained? Retaining it enables richer `->DOES` checks
and runtime introspection, but costs memory per class/role for the
lifetime of the program. A pragma or build flag could control this.

**Sorted insertion vs. sort-once.** During parsing, method and
field slots are added one at a time. We can either maintain sorted
order on each insertion (O(n) shift per insert, fine for small n)
or append unsorted and sort once before composition (O(n log n)
but only once). The sort-once approach is simpler.

**`newATTRSUB` avoidance for accessors.** The cleanest path is
a `newMETHOD_CV`-style function that compiles without installing.
The messier path is to let `newATTRSUB` install, then immediately
remove from the stash and stash in the proto-role. The former is
better but requires changes to op.c or toke.c.

**Interaction with `BEGIN` blocks and early method calls.** If
accessor CVs are not in the stash during parsing, code in `BEGIN`
blocks within the class body cannot call them. This is unlikely
to be a real concern (calling accessors at compile time on a
not-yet-sealed class is already dubious), but worth noting.

**Error message formatting.** The origin_map maps bit positions
back to stashes (for real roles) or to field declarations (for
proto-role entries with provenance). The error formatter needs
to distinguish these for rich messages like "Method 'x' conflicts
between role R and :reader for field '$x' (line 12)."
